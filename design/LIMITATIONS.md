# 项目不足与改进清单

本文档用于在阅读和理解代码的过程中，持续记录当前实现的边界、不足、实际影响和后续改进方向。记录这些问题不代表项目不可用；当前版本定位为可运行、可演示的实习项目 MVP。

这些问题的目标架构、处理顺序和验收标准见[面向生产的目标架构](PRODUCTION_ARCHITECTURE.md)。在整体框架阅读完成前，本清单只记录问题，不提前进行零散修改。

## 记录约定

- `P0`：影响正确性、安全性或核心流程，需要优先解决。
- `P1`：明显影响检索质量、稳定性或大文件处理能力。
- `P2`：增强能力或工程完善项，适合后续迭代。
- 未勾选表示尚未改进；完成改进后勾选并补充实现说明。

## ingestion/parsers.py

### 通用解析流程

- [ ] `P1` `_clean_text()` 只进行了空字符、空格和换行清洗，没有识别页眉、页脚、重复水印及乱码。重复内容可能进入多个文本块，污染检索结果。可增加重复行统计、格式感知清洗和异常字符检测。
- [ ] `P2` 连续空格会被压缩，但在代码、预格式化文本和依赖空格对齐的表格中，空格可能属于内容结构。可根据文件类型选择不同清洗策略。
- [ ] `P2` `_stable_doc_id()` 使用“文件名 + 文件内容”生成 ID，因此内容不变但重命名文件也会产生新 ID。可根据业务需求改为仅使用内容哈希，并将文件名作为独立版本信息。
- [ ] `P2` 当前只能识别完全相同的文件，无法识别内容高度相似或仅格式不同的重复文档。可增加文本指纹、SimHash 或向量相似度去重。
- [ ] `P1` 加密、损坏或格式伪造的文件主要依赖底层解析库报错，缺少细分错误类型和用户可操作的提示。可增加文件签名检查、异常分类和结构化错误信息。
- [ ] `P1` DOCX、XLSX 本质上是压缩格式，当前只有上传文件大小限制，没有专门防范解压后体积异常的压缩炸弹。可增加压缩成员数量及解压后总大小限制。
- [ ] `P2` `DocumentUnit.metadata` 会写入解析 JSON，但没有整体传递到 `ChunkDraft` 和 Milvus；当前只将 `heading`、`locator` 等关键元数据作为独立字段传递。若后续需要部门、作者、时间等动态过滤条件，需要设计可检索的 metadata Schema。

### PDF：`_parse_pdf()`

- [ ] `P1` 不支持扫描版 PDF OCR；没有文本层的页面无法生成可索引内容。可集成 PaddleOCR，并设置“文本层优先、OCR 回退”的策略。
- [ ] `P1` 双栏、跨页段落和复杂布局可能产生错误的阅读顺序。可引入版面分析模型或按文本块坐标重建顺序。
- [ ] `P1` 表格可能被提取成散乱文本，行列语义丢失。可增加 PDF 表格检测与结构化提取。
- [ ] `P2` 当前默认一页对应一个 `DocumentUnit`，没有利用 PDF 书签、字号或版面标题进一步恢复章节结构。
- [ ] `P2` 图片、图表、页眉、页脚、批注和附件没有单独处理。

### DOCX：`_parse_docx()`

- [ ] `P1` 只根据 Word 的 Heading/标题样式识别标题；仅使用加粗、字号等视觉格式制作的标题无法识别。可结合样式名、字号、加粗和段落层级判断。
- [ ] `P1` 段落和表格被分开处理，所有表格会追加在段落之后，无法保留它们在原文中的交错顺序。可遍历 DOCX XML block 元素，按原始顺序处理段落和表格。
- [ ] `P1` 图片和图片内文字未处理。可提取媒体文件并增加 OCR 或多模态描述。
- [ ] `P2` 文本框、批注、脚注、页眉和页脚未处理。
- [ ] `P2` 合并单元格可能造成文本重复，复杂表格也不能完整保留层级表头关系。
- [ ] `P2` DOCX 是流式排版格式，当前无法稳定提供真实页码，只能使用标题和表格序号溯源。

### XLSX：`_parse_xlsx()`

- [ ] `P1` 默认第一行是表头；如果前几行是报表标题、说明文字或空行，会造成错误字段名。可自动探测表头或允许用户配置表头行。
- [ ] `P1` 虽然使用 `read_only=True`，但随后执行 `list(sheet.iter_rows(...))`，仍会将整个工作表装入内存。可改为真正的流式迭代。
- [ ] `P1` `data_only=True` 读取的是文件中缓存的公式结果；未由 Excel 重新计算并保存的工作簿可能返回空值或旧值。可记录公式和值的状态，或在可信环境中增加公式计算步骤。
- [ ] `P1` 合并单元格可能导致后续单元格为空，复杂多级表头无法正确展开。
- [ ] `P2` 当前固定每 30 个有效数据行组成一个 `DocumentUnit`，没有根据表格语义或 token 数动态分组。
- [ ] `P2` 空行不会加入 `lines`，最后一组数据使用 `start_row + len(lines) - 1` 计算结束行；工作表中存在空行时，`locator` 可能与真实 Excel 行号不一致。应保存实际的首尾 `row_number`。
- [ ] `P2` 图表、图片、批注、数据验证规则和单元格样式不会进入知识库。

### Markdown：`_parse_markdown()`

- [ ] `P1` 未感知 fenced code block；代码块中以 `# ` 开头的行可能被误判为标题。可使用 Markdown AST 解析器代替逐行正则。
- [ ] `P2` 只识别 ATX 标题（`# 标题`），不识别 Setext 标题（下划线形式）。
- [ ] `P2` 表格、YAML Front Matter、引用块、任务列表和链接没有转换为更明确的结构。
- [ ] `P2` 图片只能保留 Markdown 文本或链接，无法理解图片内容。

### TXT：`_parse_text()`

- [ ] `P1` 只按 `utf-8-sig` 解码，GBK、GB18030 等编码的中文文件可能解析失败。可增加编码检测及受控回退。
- [ ] `P2` 整份 TXT 一次读入内存并先作为一个 `DocumentUnit`，不适合超大文本。可采用流式读取并按段落生成 Unit。
- [ ] `P2` TXT 缺少标题、页码等天然结构，只能依靠文件名和后续切块，引用粒度有限。可记录行号范围作为 `locator`。

## ingestion/chunker.py

- [ ] `P1` `_windows()` 使用 Python 字符数控制块大小，而模型限制通常按 token 计算；英文、中文、数字和代码的字符/token 比例不同。可使用目标 embedding/LLM tokenizer 按 token 切分。
- [ ] `P1` 父块之间的 overlap 固定为 0；上下文恰好跨越父块边界时，信息可能被拆散。可增加父块重叠，或保证父块严格在完整段落边界结束。
- [x] 已将父块全文持久化到 `data/parents/`，并在 `build_context` 节点按 `parent_id` 去重还原；上下文按近似 token budget 裁剪。
- [ ] `P1` 边界检测只识别换行、中文句号和中文分号，没有识别英文句号、问号、感叹号、冒号及 Markdown 列表等边界。
- [ ] `P1` `parent_chunk_size` 和 `child_chunk_size` 没有显式的正数校验；错误配置为 0 或负数时，`_windows()` 可能无法正常推进。应在 `Settings` 和函数入口同时校验。
- [ ] `P2` 类名为 `HeadingAwareChunker`，但切块器本身并不解析标题语义，只是依赖 parser 已经按标题生成 `DocumentUnit`，并保证不跨 Unit 切分。
- [ ] `P2` child overlap 按字符机械回退，新的子块可能从句子中间开始。可在计算重叠起点时再次寻找自然语言边界。
- [ ] `P2` `heading[:1000]` 和 `locator[:250]` 会静默截断过长字段，虽然可以满足 Milvus VARCHAR 限制，但不利于发现异常数据。可在截断时记录日志或进行结构化压缩。
- [ ] `P2` `DocumentUnit.metadata` 没有传递到 `ChunkDraft`，只能保留 `heading` 和 `locator`。
- [ ] `P2` 所有 `ChunkDraft` 一次性保存在列表中，大文档可能产生较高内存占用。可将切块、embedding 和入库改为批次或生成器流程。
- [ ] `P2` 块 ID 依赖 `parent_id`、子块序号和文本；修改切块参数后，同一文档会生成不同 ID，需要确保旧块被完整清理后再写入。

## ingestion/pipeline.py

- [ ] `P0` 文件注释称流程为 transactional，但解析文件、调用外部 embedding API、删除/写入 Milvus 和写 JSON 不能组成真正的原子事务。当前先删除旧文档再插入新文档；如果插入失败，旧版本已经丢失。可采用版本化 collection/状态字段、先写新版本再切换 active version，或实现补偿回滚。
- [ ] `P0` Milvus 插入成功后，如果解析 JSON 写盘失败，接口会返回失败，但向量数据已经存在，形成跨存储状态不一致。需要任务状态表、幂等步骤和失败补偿。
- [ ] `P1` `threading.Lock` 只在当前 Python 进程内有效；多进程、多容器部署时无法阻止同一文档并发入库。应使用数据库唯一约束、分布式锁或基于任务表的状态机。
- [ ] `P1` 锁覆盖了解析、远程 embedding、Milvus 和文件写入全过程，单个慢任务会阻塞同一进程中的其他上传。可缩小临界区，并将入库改为后台任务队列。
- [ ] `P1` `list_documents()` 通过查询最多 16384 个 chunk 后在应用层去重获得文档列表；数据量增大后可能漏掉文档，且每次入库都扫描大量 chunk。应维护独立的 document/ingestion manifest 表。
- [ ] `P1` 所有 `ChunkDraft`、文本、向量和 `ChunkRecord` 都一次性保存在内存中；大文档应按批次执行切块、embedding 和写入。
- [ ] `P1` 没有持久化任务进度、重试位置和失败状态；进程重启后只能整份重新执行，已经成功的 embedding 批次会产生重复成本。可增加 ingestion job 与 batch checkpoint。
- [ ] `P1` 以 `source` 文件名识别旧版本；不同目录、租户或部门上传同名文件时可能被当成同一文档。应引入 tenant_id、knowledge_base_id、canonical_source_id 和版本号。
- [ ] `P2` 同一 `doc_id` 已存在时直接返回 `skipped`，不会检查 Milvus chunk 是否完整、解析 JSON 是否缺失或 embedding 模型版本是否变化。应把 parser/chunker/embedding 版本加入索引版本判断。
- [ ] `P2` 替换旧版本后，旧的 `data/parsed/{doc_id}.json` 不会清理，长期运行会留下孤儿文件。
- [ ] `P2` `IngestionResult.status` 使用任意字符串，缺少枚举和更完整的错误、耗时、模型版本、块数量等审计信息。
- [ ] `P2` 当前同步 API 请求要等待整个解析与入库完成，缺少任务 ID、进度查询、取消及后台处理能力。
